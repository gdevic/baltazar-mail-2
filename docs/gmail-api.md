# The Gmail adapter

`gmail/api.js` is the Gmail extension's `api.js`, with the same exports as the Yahoo adapter (`yahoo/api.js`), so the shared client in `ext/` never knows which one it talks to. This page is how Gmail's concepts are mapped onto the client's, which endpoints are used, and what that costs.

## Sign-in

OAuth 2.0 implicit grant through `chrome.identity.launchWebAuthFlow` (`gmail/auth.js`), which Edge supports as well as Chrome. The access token lasts an hour and is kept in the extension's session storage (`gmToken`), so it survives a reload but not the browser; the address of the account signed in is kept in local storage (`gmAccount`) until Sign out. Five minutes before the token expires, or after a 401, it is renewed silently with `prompt=none` and that address as `login_hint`; that succeeds while the browser holds a Google session. A renewal is checked against the profile's address, and a token for any other account is refused, so the client never shows one mailbox while acting on another. With no account kept, nothing is tried. Only the sign-in button opens Google's window (`signIn()`); `bootstrap()` never does, so a lost session shows the sign-in page and waits. `signOut()` revokes the token at `oauth2.googleapis.com/revoke` (the token in the form body, never in the URL), which also withdraws the permission; when Google does not confirm it, the user stays signed in and is told so. Otherwise the token and the account are forgotten, a renewal already under way is ignored, and the client clears the address book and loads the page afresh. The scope is `https://mail.google.com/`, the only one that allows permanent deletion (Empty Trash and Spam, Delete in Trash). See `google-setup.md` for the client id.

## Transport

Every call goes to `https://gmail.googleapis.com/gmail/v1/users/me/...` with `Authorization: Bearer`, under the timeouts of `TIMEOUTS`. Rate limits (429, or 403 with `rateLimitExceeded`) and server errors are retried three times with backoff, honouring `Retry-After`. A Google Cloud project gives each user 6,000 quota units a minute by default (its quota page, "Units per minute per user", shows the value; Gmail's documents name 15,000), so the adapter paces every call under a sliding minute: what the user does may use 5,500 units, background work (the address-book build, `list(..., { background: true })`) only 2,500, so it never takes the room browsing needs. A refusal for quota names the minute Gmail counted in (`window_start_time`); every call then waits until that minute is over and is asked once more. Several reads go in one round trip through `POST /batch/gmail/v1` (multipart/mixed, 50 calls a batch). Gmail may refuse single items of a batch that itself succeeds; those are asked again in a batch of their own, three times with backoff. A row that still fails fails the list (only a 404 means the message is gone), since a row left out would end the paging early; a label whose counts fail keeps the counts it had. `labelIds` is a repeated URL parameter, never a comma-separated one.

Quota units of what the client does most: `messages.list` 5, `messages.get` 5 (every row of a list is one get, in a batch), `labels.get` 1, `history.list` 2, `messages.modify` 5, `batchModify` 50, `drafts.create` or `send` 10 to 100. A page of 100 rows seen for the first time is about 505 units; seen before, 5 (see the row cache below). A poll is 2 + the number of shown labels + 2; the Starred count is 1, `labels.get` of `STARRED` (`starredCount()`), where a search would fetch every starred message.

## Folders are labels

| Client | Gmail |
|---|---|
| Inbox, Drafts, Sent, Spam (type `BULK`), Trash | the system labels `INBOX`, `DRAFT`, `SENT`, `SPAM`, `TRASH` |
| All Mail (type `ARCHIVE`, id `ALL`) | no label: `messages.list` without `labelIds`, which excludes Spam and Trash |
| a user folder, path `Parent/Child` | a user label, whose `name` is already that path |
| a folder's `unread` and `total` | `labels.get` `messagesUnread` and `messagesTotal`, one batch per `folders()` |
| hidden folder (type `INVISIBLE`) | a user label with `labelListVisibility: labelHide` |
| not shown at all | `STARRED`, `UNREAD`, `IMPORTANT`, `CHAT`, `CATEGORY_*` |

`highestModSeq`, which the client compares to see whether a folder changed since the last poll, is synthesised: each `folders()` call asks `history.list` from the last history id seen, and every label named in a record (`messagesAdded`, `messagesDeleted`, `labelsAdded`, `labelsRemoved`), plus All Mail, gets the newest history id as its stamp; a change in a label's counts stamps it too. A history Gmail no longer holds (404, after about a week away) stamps every folder once. The new-mail dot uses Inbox's `messagesUnread`, which is exact.

Folder operations: `labels.create` with `labelListVisibility: labelShow`; `labels.patch` for rename and move (the new name is the new path), repeated for every label nested under the old path, since Gmail does not rename those itself; `labels.delete`; Empty Trash or Spam is `messages.list` of the label followed by `batchDelete`, a thousand at a time; Mark all read is `messages.list` with `labelIds=[label, UNREAD]` followed by `batchModify`.

## Rows and bodies

A list is `messages.list` (`labelIds`, `q`, `includeSpamTrash` for Spam and Trash) for ids, then one batch of `messages.get?format=full` with a `fields` mask that leaves the part data out, so a row costs the same 5 units as metadata would and still knows its attachments. A message's headers and parts never change (a draft saved again is a new message), so each row is fetched once and kept, up to 5,000; its labels, which do change, come from what the adapter keeps per message, which its own changes and every record of Gmail's history keep current. A refresh, or a folder opened again, then fetches only the messages it has not seen. A history Gmail no longer holds drops the kept rows and labels. Paging: the client asks by offset, Gmail answers with tokens, so the adapter keeps, per query, the token of where its last page ended; any other offset is walked to from the start with id-only list calls. A request for more than Gmail's 500 ids a page (a refresh of many loaded rows) follows the tokens until it has them all. A row's `folder` is the listed label, or for a search result Trash, Spam, Drafts, Inbox, the first user label, Sent, or All Mail, in that order. Address headers are parsed by `rfc822.js` (`parseAddresses`): display names with quotes, comments, groups and RFC 2047 words.

`body()` is `messages.get?format=full` with the data. The text is read from the MIME tree as a mail reader does: an alternative gives its HTML branch (its plain-text branch for `text`), a related part its root, and any other multipart every text part in order, so text after an attachment is shown too; each part is decoded by its charset, and plain text becomes escaped HTML with links. Attachments are the other leaves with a file name or a Content-ID, with Gmail's `partId` and, kept privately, their `attachmentId`. A part is inline only when the HTML shows it as a `cid:` source; Content-Disposition does not decide it, since some mailers mark every attachment inline. A row, which has no HTML, counts a Content-ID part inside `multipart/related` as inline. Inline images are `cid:` references to those parts: the client asks `inlineSource()` for each, which fetches the part through `messages.attachments.get` and answers a data: URL. Attachment bytes (`partBytes()`) come the same way; a thumbnail is the image itself when it is under 2 MB. Gmail has no document converter and no text extraction, so the viewer shows "no preview available" with Download for formats it cannot draw itself.

Remote images: Gmail returns the sender's HTML as it is, so when the reader loads images they load from the senders' hosts. `IMAGE_SRC` is `https:`.

## Search

Gmail's search takes any boolean query, so the dialect writes the whole parsed search out (`dialect.compile`): words and quoted phrases, `-` for NOT, `OR`, parentheses, `from:`, `to:`, `subject:`, `has:attachment`, `is:starred`, `is:unread`, `is:read`, `after:YYYY/MM/DD`, `before:`. The client never needs `query.js`'s evaluation. A folder alone is searched with `labelIds`; a folder with its subfolders through the query, as `(label:"Parent" OR label:"Parent/Child")`, names in quotes with spaces as hyphens; "elsewhere" is the search with `-label:` terms for the scope, with the answer filtered once more by `labelIds` in case Gmail read a name differently. Starred is `is:starred`; a person's mail is `(from:a OR to:a OR cc:a)`; "unread in a folder" names the label outside the query.

## Actions

Read, unread, star and unstar change the `UNREAD` and `STARRED` labels: up to ten messages one each with `messages.modify` (5 units each, in one batch, each answered on its own), more with `messages.batchModify` (50 units for up to a thousand, all or none). A move takes away `INBOX`, `SPAM` and `TRASH`, and the user label of the folder the message is shown in (the client passes it as `from`), and adds the target's label; a move to All Mail adds nothing, which is Gmail's archive. The message's other user labels stay, as Gmail keeps them, also through Trash and Spam, whose messages no label's list shows. The answer carries `undo()`, which takes back exactly the labels the move added and removed, so the client's undo restores the message as it was rather than moving it to one folder. Permanent deletion is `batchDelete`, or `drafts.delete` for a draft. The labels of a message not yet seen are fetched first with `format=minimal`.

## Drafts and sending

The message is built as RFC 822 by `rfc822.js build()`: the headers, `Message-ID`, `In-Reply-To` and `References` from the original (fetched once with `format=metadata`), the body as quoted-printable `text/html` or `text/plain`, inline images in a `multipart/related` with their Content-ID, files in a `multipart/mixed`; forwarded attachments are fetched with `partBytes()` and embedded. It goes up as `uploadType=multipart`: a JSON part naming the thread and, for a draft, its id, then the message.

A draft keeps its draft id across saves while Gmail gives it a new message id each time, so the client's `csid` is the draft id: the first save is `drafts.create` and returns `csid: <draft id>`, which the composer adopts; later saves are `drafts.update`. Draft rows and bodies carry the draft id too, from `drafts.list`, so a reopened draft saves into the same draft and Discard deletes it. The answer names no stored parts, so the composer uploads every file again with each save, which keeps the draft whole. A reply joins the original's thread only while the subjects still match (Gmail's rule); otherwise the message starts a thread, and a thread Gmail refuses is tried once without. Send is `drafts.send` when a draft exists, else `messages.send`; Gmail files the copy in Sent and removes the draft. A draft deleted or sent elsewhere (404) is saved as a new draft, or sent with `messages.send`. A Send pressed while the first save is still uploading waits for it and sends the draft it created. Undo-send stays the client's own timer. Gmail has no "answered" flag to set on the original.

Accounts come from `getProfile` and `settings.sendAs.list`: the primary address and the verified aliases, each with its display name, signature and reply-to.

## Limits worth knowing

`LIMITS.messageBytes` is 25 MB of attachments, Gmail's own send limit. `LIMITS.scanMax` is 2,000 rows per folder for the first address-book build, since every row costs quota; at the background pace (about five pages of 100 rows a minute) the first build of Inbox and Sent takes about eight minutes; later builds stop at the newest row already seen. Label names reach the search only in a folder-with-subfolders scope, in quotes; a name with a double quote in it cannot be searched that way.
